# Training Data Contract

Version: `v1`  
Source batch: `C:\STS2_RL\Combat\data\trajectories_train500_20260722_w4`  
Export root: generated by `Training/export_training_dataset.py`

## Purpose

This contract defines the boundary between:

- RL side: Emulator integration, trajectory generation, quality classification, export
- Training side: dataset loading, state/action encoding, model, loss, training, evaluation

The training side must be able to read the export without starting Emulator or pythonnet.

## File Layout

Under one export root, for example:

`C:\STS2_RL\Training\exports\train500_export_20260722_v1`

- `export_metadata.json`
- `quality_report.json`
- `REPORT.md`

## Identity Rules

- One trajectory corresponds to one Scenario run.
- `trajectory_id` is the stable export/run-level identifier for one realized trajectory row-set.
- `scenario_id` is the source-scenario identifier and is allowed to diverge from `trajectory_id` in future exports.
- Current exports may set `scenario_id == trajectory_id`, but consumers must not depend on that equality.
- One decision row is uniquely identified by:
  - `decision_id = "{trajectory_id}:{decision_index}"`

`decision_index` is zero-based within a single trajectory.

## Observation Schema

Each exported decision stores:

- `observation`: raw observation-state dict at the decision point

This is copied from the saved RL trajectory row and is intentionally not tensorized here.

Important observation subfields commonly used by training code:

- player:
  - `characterId`
  - `hp`, `maxHp`, `block`, `energy`, `stars`
  - `orbSlots`, `orbs`
  - `playerPowers`
  - `relics`
  - `potions`
- piles:
  - `hand`
  - `drawPile`
  - `discardPile`
  - `exhaustPile`
  - `playPile`
  - `deck`
- enemies:
  - `enemies[*].id`
  - `enemies[*].hp`, `maxHp`, `block`
  - `enemies[*].intent`
  - `enemies[*].powers`
  - `enemies[*].index`
- control state:
  - `stepIndex`
  - `pendingChoice`

Observation is the authoritative game-state payload for training input design.

## LegalActions Schema

Each exported decision stores:

- `legal_actions`: normalized list of legal action dicts

Each legal action has:

- `action_id`
- `action_type`
- `label`
- `is_available`
- `card_id`
- `potion_id`
- `target_type`
- `target_enemy_index`
- `raw_parameters`
- `action_id_scope`

Notes:

- `label` is display/debug text only.
- `label` must not be treated as a stable semantic ID.

## Teacher Action Schema

Each decision stores:

- `teacher_action`
- `teacher_action_type`
- `teacher_target`
- `teacher_score`

`teacher_action` uses the same normalized structure as `legal_actions`.

`teacher_target` currently includes:

- `selected_enemy_index`
- `selected_action_index`

## Candidate Action Scores

Each decision stores:

- `candidate_actions`

Each candidate includes:

- `action_id`
- `label`
- `target_index`
- `enemy_index`
- `score`
- `skipped_reason`
- `exception_type`
- `exception_message`
- `is_training_target_eligible`
- `score_scope`

This is the RL-side candidate evaluation surface. It is suitable for:

- policy-target inspection
- ranking-loss experiments
- action-mask debugging

Rules:

- `candidate_actions.score` is primarily for comparison among candidates within the same decision.
- `candidate_actions.score` must not be interpreted as a globally calibrated value across different decisions or trajectories.
- candidates with `skipped_reason != null` are not training targets.
- candidates with `exception_type != null` are not training targets.
- `is_training_target_eligible == false` candidates must not be used as supervised targets.

## Action ID Stability

`action_id` must **not** be treated as a globally stable class id.

It is:

- valid only within the current decision state's legal-action set
- generated by Emulator for that state
- not stable across different states
- not guaranteed to map to a fixed semantic action class

Training code should treat:

- `action_type`
- `card_id`
- `potion_id`
- target metadata

as the semantic action representation.

`action_id` is still exported for exact replay/debugging, not for fixed-class supervised labels.
`label` is also exported for exact replay/debugging and human inspection only.

## Optional and Missing Fields

Missing values are represented as JSON `null`.

Common optional fields:

- `teacher_score`
- `card_id`
- `potion_id`
- `target_enemy_index`
- `pendingChoice`
- `associatedCard` inside powers

Training code must handle `null` safely.

## Inclusion / Exclusion Rules

Initial supervised dataset targets:

- include: `usable_complete`
- exclude:
  - `usable_partial` from the primary complete dataset
  - `exclude_state_mismatch`
  - `exclude_cycle`
  - `exclude_emulator_issue`
  - `exclude_heuristic_exception`
  - `missing_mad_science_state`
  - `missing_associated_card`

`usable_partial` is exported separately and preserved for future use, but not mixed into the initial complete dataset.

Additional filtering rule:

- any decision with empty `legal_actions` is not a valid supervised learning row and must be excluded from the training-target set

## Dictionary Versioning

`id_dictionaries.v1.json` contains versioned dictionaries for:

- action types
- cards
- potions
- powers
- relics
- enemies
- encounters
- characters

Rules:

- id `0` is reserved for `__UNKNOWN__`
- existing ids are fixed once released
- new tokens must be appended at the end without changing existing ids
- rebuilding a dictionary in a way that changes an already-issued id requires a new major dictionary version
- append-only token growth is a backward-compatible change within the same major version
- regeneration from the same source data should not reorder ids

Compatibility summary:

- compatible minor change:
  - append new token(s) at tail only
- incompatible major change:
  - reorder ids
  - reuse an existing id for another token
  - remove a token without a version bump

The current exporter still discovers tokens from source data, but released dictionary files are governed by the append-only compatibility rule above.

## Train / Validation / Test Split

Split is by trajectory, never by individual decision.

Default ratio:

- train: 80%
- validation: 10%
- test: 10%

Split seeds are stored in `export_metadata.json`.

## Validation Rules

The exporter / validator contract requires:

- teacher action must exist in `legal_actions`
- teacher action must have `is_available == true`
- `selected_action_index` must be within `legal_actions` bounds when present
- `decision_id` must be unique within an export
- one trajectory must belong to exactly one split
- decisions with empty `legal_actions` are not valid learning targets
- skipped/exception candidates are not valid learning targets

## Known Initial Constraints

- `action_id` is state-local and not a stable label id
- `usable_partial` is not in the primary complete dataset
- `missing_mad_science_state` remains a data-collection limitation, not an encoded guess
- some residual error repros still exist in the source batch and are intentionally excluded from the complete export
